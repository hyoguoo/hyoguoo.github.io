결제 도메인 학습 프로젝트인 [Payment Platform](https://github.com/hyoguoo/payment-platform)은 결제 요청을 먼저 접수하고, 승인은 뒤에서 비동기로 처리한다. 브라우저는 접수 응답을 받은 뒤 결제 상태를 조회해 완료를 확인한다.

<PgPaymentOverview />

처리량을 측정하기 전에 지켜야 할 목표부터 정했다. 운영 서비스가 아니므로 [PayPal 연동 가이드][paypal-monitoring]의 모니터링 예시(주문 생성 응답 2초, 결제 확정 응답 3초 미만)를 참고해 가상의 서비스 수준 목표(SLO)를 세웠다.

| 구간 | 목표 |
| :---: | :---: |
| 주문 생성·결제 접수 응답 | p95 500ms 이하 |
| 화면의 완료 확인 (1초 간격, 최대 30회 조회) | p95 3초, p99 5초 이하 |
| API 오류, 결제·재고 불일치 | 0건 |

변경 전 서버는 이 목표를 지키지 못했다.

- **화면의 완료 확인**: 초당 100건에서 30번 조회하는 동안 완료를 확인한 주문이 **18,001건 중 411건**뿐이었다.
- **처리량**: 요청을 늘릴수록 오히려 줄었다. 초당 160건을 보내면 102건만 처리했다.

병목을 찾아 수정하고 같은 조건으로 다시 측정하는 과정을 네 번 반복했다.

| 기준 | 변경 전 | 최종 |
| :---: | :---: | :---: |
| 초당 100건, 화면의 완료 확인 | 30회 조회 안에 411 / 18,001건 | **p95 2.06초, p99 3.14초** |
| 초당 100건, 결제 접수 응답 p95 | 530ms | **66ms** |
| 안정 처리한 가장 높은 요청 속도 | 초당 120건 | **초당 180건** |
| 초당 160건 요청, 부하 중 결제 완료 | 초당 102.3건 | **초당 159.7건** |
| 결제·재고 전수 대조 | 일치 | 일치 |

> **측정 환경**: 모든 수치는 노트북 한 대에서 측정했다.
>
> - **서버**: 서비스·DB·Kafka 등 컨테이너 20개 (Docker CPU 10코어 할당)
> - **부하**: k6도 같은 노트북에서 실행
> - **외부 PG**: 응답을 100\~300ms 늦게 주는 모의 PG
>
> 운영 환경의 처리량이 아니라, 같은 장비·같은 조건에서 변경 전후를 비교한 값이다. 자세한 조건은 [글 끝](#측정-환경과-참고-자료)에 정리했다.

이 글에서는 다음 세 가지를 차례로 살펴본다.

1. **요청이 늘수록 처리가 느려진 이유**: 승인 결과를 단일 스레드로 반영하던 구조
2. **상한 복원 뒤 워커 수 튜닝**: 상한이 생기며 드러난 워커 부족과 적정 워커 수
3. **최종 처리 한계**: 초당 120\~140건에서 180\~200건으로 올라간 구간

## 결제 한 건이 거치는 단계

결제 한 건은 서비스 세 곳을 거쳐 처리되고, 서비스 사이에는 Kafka 메시지로 작업을 전달한다. 받는 쪽의 처리 속도가 메시지가 들어오는 속도보다 느리면, 처리되지 않은 메시지가 토픽에 쌓인다. 따라서 **어느 단계 앞에 미처리 메시지가 쌓이는지 보면 병목 위치를 찾을 수 있다.**

<ThroughputPipeline title="결제 한 건이 거치는 여섯 단계" />

PG 서비스는 수신한 작업을 DB에 먼저 저장한 뒤 메모리 대기열에 넣고, 워커가 대기열에서 작업을 꺼내 처리한다. 워커는 두 종류다.

- **승인 워커**: 외부 PG에 승인을 요청한다.
- **결과 발행 워커**: 승인 결과를 결제 서비스로 보낸다.

<ThroughputWorkerQueue />

이 구조를 처음 만든 과정은 [비동기 결제 처리 플로우 구현](/blog/async-payment-flow/)에 정리했다.

## 측정 방법

### 서버 처리량 테스트와 사용자 화면 테스트

서버의 처리 한계와 사용자가 겪는 시간을 따로 확인하도록 테스트를 두 가지로 나눴다.

| 구분 | 서버 처리량 테스트 | 사용자 화면 테스트 |
| :---: | :---: | :---: |
| 확인하는 것 | 서버가 감당할 수 있는 요청 속도 | 사용자가 완료를 보기까지 걸린 시간 |
| 요청 방식 | 정해진 속도로 결제 요청만 보냄 | 결제 요청 뒤 1초마다 상태 조회 (최대 30회) |
| 판정 | 부하 중 적체 없이 안정 처리하는가 | 완료 확인 p95 3초·p99 5초, 접수 응답 p95 500ms 이하, 오류 0건 |

- **상태 조회 분리**: 상태 조회도 서버 자원을 사용하므로, 서버의 처리 한계는 조회 없이 측정했다.
- **완료 대기 없음**: 완료를 기다리면 요청 간격이 밀려 부하 도구의 한계를 측정하게 된다. 그래서 요청만 보내고 완료 건수는 DB에서 따로 집계했다.

### 처리 한계 판정

각 요청 속도를 3분 동안 유지하며, 아직 완료되지 않은 결제 건수를 약 10초 간격으로 기록했다. 결과는 두 가지 형태로 나뉜다.

<ThroughputJudgement />

- **안정 처리**: 시작 직후에는 밀리더라도, 요청을 보내는 동안 밀린 결제가 줄어 낮은 수준을 유지한다.
- **적체 누적**: 요청을 보내는 내내 밀린 결제가 늘고, 요청을 멈춘 뒤에야 줄어든다.

처리 한계는 **안정 처리한 가장 높은 속도와 적체가 누적된 가장 낮은 속도 사이**로 판정했다. 적체가 누적된 속도는 요청을 멈춘 뒤 결국 모두 완료되더라도 처리할 수 있는 속도로 보지 않았다.

## 요청이 늘수록 처리가 느려진 이유

### 보낸 만큼 처리하지 못한 구간

변경 전 서버로 서버 처리량 테스트를 한 결과다.

<ThroughputRateDrop />

요청을 늘릴수록 처리량이 오히려 줄었다.

- **초당 120건**: 안정 처리했다.
- **초당 140건, 160건**: 밀린 결제가 3분 내내 늘었고, 처리량은 초당 109.5건, 102.3건으로 떨어졌다.

그런데 요청을 멈추자 같은 서버가 밀린 결제를 초당 약 240건씩 처리했다. **처리 능력은 충분했지만, 요청이 들어오는 동안에는 그 속도를 내지 못했다.**

원인을 좁힐 단서는 두 가지였다.

- **DB 커넥션 대기**: 사용자 화면 테스트에서 함께 늘어 처음에는 DB 커넥션 부족을 의심했다. 하지만 상태 조회가 없는 서버 처리량 테스트에서는 거의 없었다.
- **메시지 적체**: 서버 처리량 테스트에서도 결과 반영 앞에 승인 결과 메시지가 쌓였다. 초당 160건 회차에서 최대 약 1만 건이었다.

상태 조회 없이도 나타난 쪽은 결과 반영 앞의 적체였다. 그래서 DB 커넥션보다 결과 반영을 먼저 살펴봤다.

<ThroughputPipeline title="변경 전 병목: 결과 반영" highlight={['result']} />

### 결과 반영 스레드의 처리 시간

결제 서비스는 승인 결과 메시지 한 건마다 세 가지 작업을 처리한다.

1. **결제 완료 저장**: DB에 결제 완료를 기록한다.
2. **재고 확정 메시지 발행**: 상품 서비스로 재고 확정 메시지를 보낸다.
3. **커밋**: 이 메시지까지 읽었다는 위치를 함께 기록하고, 세 작업을 한 번에 커밋한다.

세 작업은 함께 성공하거나 함께 실패한다. 결제는 완료됐는데 재고 메시지만 빠지는 일은 생기지 않는다.

문제는 이 일을 하는 스레드가 **1개**였다는 점이다. 스레드는 메시지 한 건을 끝내야 다음 건을 꺼낸다.

스레드의 사용율은 Micrometer가 내보내는 지표로 계산했다.

| 지표 | 측정하는 것 |
| :---: | :---: |
| `spring_kafka_listener_seconds` | 리스너가 메시지 한 건을 처리한 시간 |
| `kafka_producer_txn_*` | 읽은 위치 기록과 트랜잭션 커밋에 걸린 시간 |

두 시간을 더한 메시지당 처리 시간에 초당 처리 건수를 곱하면 스레드 사용률이 된다. 초당 140건 부하에서 구간별로 측정한 결과는 다음과 같다.

<ThroughputMessageTime />

> **스레드 1개의 한계**: 1초 ÷ 메시지당 약 8ms ≈ 초당 약 125건
>
> 부하 중 사용률은 8.1ms × 초당 121.2건 ≈ 98%였다. 초당 120건은 안정 처리하고 140건부터 적체가 누적된 결과와 일치한다.

초당 140건을 보내면 승인 결과 메시지도 초당 140건씩 도착한다. 결과 반영 스레드는 그중 약 120건까지만 처리하므로, 나머지가 결과 반영 앞에 쌓인다.

<ThroughputSlowdownChain />

요청이 많을수록 처리량이 더 떨어진 이유는 건당 처리 시간이 부하에 따라 달라졌기 때문이다. 스레드가 1개라 건당 시간이 길어지면 처리 상한도 그만큼 낮아진다.

| 상황 | 건당 처리 시간 | 스레드 1개의 상한 (1초 ÷ 건당 시간) |
| :---: | :---: | :---: |
| 요청을 멈춘 뒤 | 약 4.2ms | 초당 약 240건 |
| 부하 중 | 약 8ms | 초당 약 125건 |
| 부하 첫 60초 | 약 13ms | 초당 약 77건 |

요청이 들어오는 동안에는 DB와 Kafka의 응답이 느려져 건당 시간이 두세 배로 늘었다. 요청을 멈추자 밀린 결제를 초당 약 240건씩 처리한 것도 건당 시간이 다시 짧아졌기 때문이다.

같은 측정에서 다른 후보는 여유가 있었다.

| 후보 | 측정값 |
| :---: | :---: |
| DB 커넥션 | 커넥션 대기 평균 0.07ms 이하 |
| 결제 명령 발행 | 건당 0.7\~1.6ms |
| CPU | 한계에 닿은 컨테이너 없음 |

### 주문 순서를 지키는 스레드 증설

스레드를 늘려도 **같은 주문의 메시지는 도착 순서대로 처리돼야 한다.** Kafka의 파티션이 이를 보장한다. 같은 주문의 메시지는 주문 번호에 따라 늘 같은 파티션에 들어가고, 파티션 하나는 스레드 하나만 맡는다.

<ThroughputPartitions />

결과 메시지 토픽의 파티션 수에 맞춰 리스너의 동시 처리 스레드 수를 1개에서 3개로 늘렸다.

<ThroughputThreadCompare />

초당 140건까지는 안정 처리했지만, 160건부터는 다시 적체가 누적되기 시작했다.

### 스레드 증설로 함께 사라진 DB 커넥션 대기

스레드를 3개로 늘리자, 처음에 의심했던 DB 커넥션 대기도 함께 사라졌다. DB 커넥션 풀 설정은 따로 바꾸지 않았다.

<ThroughputLoopFix />

DB 커넥션 대기는 원인이 아니라 결과 반영이 밀리면서 생긴 증상이었다. 스레드 1개일 때도 상태 조회가 없는 서버 처리량 테스트에서는 대기가 없었다.

<ThroughputQueryCompare />

상태 조회가 있는 테스트에서는 결과 반영이 밀리는 순간 아래 악순환이 시작됐다. 결과 반영이 밀리지 않으면 이 순환은 처음부터 생기지 않는다.

<ThroughputFeedbackLoop />

## 다음 병목: 명령 수신과 워커 상한

### 결과 반영 다음으로 메시지가 쌓인 곳

스레드 3개로 초당 160건을 보내자 다른 모습이 나타났다.

- 처리량이 초당 141.6건에서 멈췄다.
- 밀린 결제 약 2,500건이 부하 중에 줄지 않았다.
- 결과 반영 스레드의 사용률은 각각 절반 수준이었다.

메시지가 쌓이는 위치도 **결과 반영 앞에서 명령 수신 앞으로** 옮겨 갔다.

- **스레드 1개**: 결과 반영 앞(승인 결과 메시지)에 최대 약 1만 건이 쌓였다.
- **스레드 3개**: 결과 반영 앞은 100\~300건으로 줄었고, 대신 명령 수신 앞(결제 명령 메시지)에 2,200\~3,400건이 쌓였다.

<ThroughputPipeline title="결과 반영 개선 뒤 병목: 명령 수신" highlight={['command']} />

명령 수신 역시 메시지를 스레드 1개로 처리하고 있었다. 스레드 수를 별도로 설정하지 않아 Spring Boot 기본값 1이 적용된 상태였다.

결과 반영과 같은 구조이므로 해결 방법도 같다. 결제 명령 토픽 역시 주문 번호 기준으로 파티션 3개에 나뉘므로, 주문별 처리 순서를 유지한 채 리스너의 동시성을 3으로 지정했다.
### 동시 처리 상한이 없던 워커

PG 서비스 코드를 점검하다가 문제를 하나 더 찾았다. 측정에서 병목으로 나온 적은 없지만, 실제 PG에서는 위험할 수 있는 문제였다. **워커가 작업을 직접 처리하지 않고, 작업마다 새 스레드를 만들어 넘기고 있었다.**

```java
// 변경 전: 꺼낸 작업을 새 가상 스레드에 넘기고 바로 다음 작업을 꺼낸다
J job = takeJob();
executor().submit(() -> runWithContext(job));

// 변경 후: 꺼낸 작업을 워커가 직접 처리한다
J job = pollJob(POLL_TIMEOUT_MILLIS, TimeUnit.MILLISECONDS);
if (job != null) {
    runWithContext(job);
}
```

워커는 작업을 넘기자마자 다음 작업을 꺼내므로, 워커를 몇 개로 정하든 동시에 실행되는 작업 수에는 제한이 없었다.

<ThroughputWorkerModel />

상한이 없으면 외부 PG나 DB가 느려질 때 문제가 커진다.

- **외부 PG**: 동시에 보내는 요청이 계속 늘어난다. 실제 PG에는 동시 요청 한도가 있을 수 있다.
- **DB**: 커넥션을 기다리는 작업이 계속 늘어난다.

모의 PG는 늘 100\~300ms 안에 응답해서 지금까지의 측정에는 나타나지 않았다.

그래서 원래 설계대로 워커가 작업을 직접 처리하도록 되돌렸다. 이렇게 하면 **동시에 처리하는 작업 수가 워커 수를 넘지 않는다.**

## 상한 복원 뒤 워커 수 튜닝

### 두 변경 적용 후 측정 결과

두 변경을 함께 적용하고 다시 측정했다.

- **명령 수신**: 스레드 1개 → 3개
- **워커**: 상한 복원. 승인 워커 수는 측정 전에 임시로 둔 기본값(5개)이라, 32개와 64개로 각각 측정해 정하기로 했다.

<ThroughputWorkerRounds />

명령 수신 앞의 적체는 사라졌지만, **두 회차 모두 처리량이 변경 전(초당 141.6건)보다 오히려 낮았다.** 상한이 생기면서 그 뒤 단계의 워커가 부족해졌기 때문이다.

### 승인 워커 32개: 외부 PG 응답 시간이 만든 한계

승인 워커는 32개로 시작해, 부족하면 늘려 가며 맞추기로 했다. 32개는 평균 PG 응답 시간(약 200ms)으로 초당 160건을 처리하는 데 필요한 수다.

> 초당 160건 × 0.2초 = 동시에 처리할 승인 32건

상한이 생겼으므로 동시에 처리할 수 있는 승인 요청은 워커 수만큼이다.

| 항목 | 값 |
| :---: | :---: |
| 동시에 처리하는 승인 | 32건 (= 워커 수) |
| 승인 한 건에 걸리는 시간 | 100\~300ms (PG 응답) |
| 계산상 처리량 | 초당 약 107\~320건 |
| 실측 처리량 | **초당 145\~149건** (요청은 초당 160건) |

들어오는 요청보다 처리량이 낮아 작업이 넘쳤다.

- **대기열**: 처리하지 못한 작업이 1,024칸을 가득 채웠다.
- **넘친 작업**: 폴링 워커가 DB에서 다시 꺼낼 때까지 기다렸다.

승인 워커를 64개로 늘리자 대기열이 비었고, 승인 단계는 초당 160건을 안정 처리했다.

### 승인 워커 64개: 결과 발행 워커 1개의 한계

승인 단계가 부하를 따라가자, 이번에는 바로 다음 단계인 결과 발행 워커가 병목이 됐다. 결과 발행 워커는 1개뿐이어서 초당 143\~146건 이상은 발행하지 못했다.

<ThroughputPipeline title="상한 복원 뒤 병목: 결과 발행 워커" highlight={['publish']} />

결과 발행 워커는 상한을 되살리기 전에도 1개였다. 같은 1개인데 그때는 병목이 아니었던 이유는 동작 방식에 있다.

| 시점 | 설정 | 실제 동작 | 동시 발행 |
| :---: | :---: | :---: | :---: |
| 상한 복원 전 | 워커 1개 | 작업마다 새 가상 스레드로 넘김 | 제한 없음 |
| 상한 복원 후 | 워커 1개 | 워커가 직접 발행 | 1건, 초당 약 145건에서 정체 |

설계는 워커 수만큼만 동시에 처리하는 구조였지만, 코드는 상한 없이 동작하고 있었다. 그래서 결과 발행 워커 수 1이 적절한지는 한 번도 검증된 적이 없었다. **코드를 설계대로 고치자 이 설정값이 처음으로 실제 한계가 됐다.**

승인 워커 32개 회차에서는 승인 단계가 먼저 한계에 닿았기 때문에, 결과 발행 워커의 한계는 64개 회차에서 처음 확인됐다.

### 결과 발행 워커 8개: 초당 160건 안정 처리

결과 발행 워커를 8개로 늘리고 다시 측정했다. 승인 워커는 64개 그대로다.

| 항목 | 상한 복원 전 | 승인 워커 64 + 결과 발행 워커 8 |
| :---: | :---: | :---: |
| 초당 160건, 부하 중 결제 완료 | 초당 141.6건 | **초당 159.7건** |
| 요청을 멈춘 뒤 밀린 결제 처리 | 16.0초 | **0.3초** |
| 대기열을 넘친 작업 | — | **0건** |
| 전수 대조 | 일치 | 일치 |

최종 코드로 한 번 더 측정해도 결과는 같았다.

- **서버 처리량 테스트**: 초당 159.7건
- **사용자 화면 테스트**: 초당 100건에서 두 번 모두 목표 통과

### 워커 증설 뒤 정리한 DB 커넥션 사용 구간

처리량에는 영향이 없었지만, 워커를 늘리면서 함께 고친 위험 경로가 있다. **워커는 64개, DB 커넥션 풀은 30개**라서 커넥션을 오래 잡는 작업이 생기면 커넥션이 부족해질 수 있다.

평소 승인 처리는 PG를 호출하는 동안 커넥션을 쓰지 않는다. 문제는 PG가 "이미 처리된 결제"라고 응답해 상태를 다시 조회하는 경우였다.

<ThroughputTxScope />

조회를 트랜잭션 밖으로 옮겨, 이 경우에도 결과를 반영할 때만 커넥션을 쓰도록 바꿨다.

## 최종 처리 한계

최종 코드로 초당 180건과 200건을 측정했다.

<ThroughputBoundary />

| 요청 속도 | 부하 중 결제 완료 | 판정 |
| :---: | :---: | :---: |
| 초당 180건 | 초당 179.7건 | 안정 처리 |
| 초당 200건 | 초당 184.1건 | 적체 누적 |

- **처리 한계 구간**: 초당 120\~140건 → **180\~200건**
- **초당 160건 처리량**: 102.3건 → **159.7건** (약 1.56배)

## 마치며

처리량이 요청을 따라 늘지 않은 원인은 작업을 하나씩 처리하던 지점이었다. 결과 반영 스레드, 명령 수신 스레드, 결과 발행 워커가 차례로 한계에 닿았고, 하나를 풀면 바로 다음 지점이 새 한계가 됐다. 이 지점들을 찾아 늘린 결과, 처리 한계는 초당 120\~140건에서 **180\~200건**으로 올라갔고 초당 100건에서 사용자 완료 확인 목표도 통과했다.

### 회차 운영 조건

변경 전후를 비교하기 위해, 바꾼 설정 외의 조건은 회차마다 같게 유지했다.

- **새 환경**: 컨테이너·DB·Kafka를 새로 띄우고 같은 상품·재고 데이터를 넣는다. 본측정 전 2분 동안 초당 10건으로 예열한다.
- **휴식 시간**: 직전 회차가 끝나고 10분 이상 쉰 뒤 시작한다. 연속 측정으로 CPU 온도가 올라 결과가 달라지는 것을 막기 위해서다.
- **전수 대조**: 회차가 끝나면 모든 주문의 결제·재고 데이터를 대조해 돈과 재고가 맞는지 확인한다.
