About

주문 확정부터 PG사 승인, 최종 재고 반영까지 전자상거래 결제의 전 과정을 구현한 백엔드 플랫폼이다.
결제 한 건을 4개의 마이크로서비스가 Kafka 메시지로 이어받아 처리하고, 어느 지점에서 실패해도 복구되도록 설계했다.
실서비스 제품이 아니라, 분산 환경에서 결제와 재고의 정합성을 지키는 방법을 동작하는 코드로 검증한 1인 학습 프로젝트다.
본문의 모든 수치는 부하 테스트(k6)와 CI 검증에서 나온 실측값이다.

비동기 처리(202 Accepted) 설계 의도

기존 동기 방식의 한계결제 확정 API가 PG사의 응답을 동기적으로 대기할 경우 사용자는 수 초간 로딩 화면에 갇히게 되며(이 대기는 곧 구매 이탈로 이어진다),
PG사에 장애가 발생하면 결제 서비스 전체의 가용성이 연쇄적으로 저하된다.
비동기 아키텍처 전환요청 접수 즉시 202 Accepted를 반환하고, 실제 승인 처리는 백그라운드에서 비동기로 수행한다. 클라이언트는 주문 상태를 폴링(Polling)하며,
외부 PG사의 응답 지연이나 장애가 사용자 경험(응답성)에 직접적인 영향을 주지 않는다.
성능 개선 지표동일 로직을 동기·비동기 두 방식으로 구현하여 k6 부하 테스트를 진행했다. 외부 PG 지연 환경 기준 비동기 방식의 TPS가 약 47.5% 우수했으며, 사용자 체감 응답 시간은 1,150ms에서 150ms 수준으로 단축되었다. 순간적인 부하 집중 상황에서도 유실 없이 요청을 처리함을 입증했다.
측정 모델과 시행착오는 벤치마크 보고서 ↗에 있다.
202 응답의 정합성 보장202 응답은 두 가지 선행 조건의 완수를 의미한다.
재고가 안전하게 선점되었고, PG사 결제 요청 명령이 Outbox(발행 대기열)에 안전하게 적재되었음을 보장한다.
응답 직후 서버 장애가 발생하더라도, 영속화된 이 두 상태를 기반으로 처리는 누락 없이 재개된다.

    PG 명령 처리와 재시도

    결제 명령을 받아 PG사를 호출하고, 실패 시 재시도하며, 한도 초과 시 격리하는 전체 절차다.
    이 아키텍처의 핵심 기능 중 하나로서,
    지연 큐나 별도 스케줄러 없이 오직 Kafka 재발행만으로 재시도 메커니즘을 구현했다.

    명령 처리 파이프라인

    정상 흐름과 장애 복구 경로 통합

    화면 낭독기용 요약: 명령을 받으면 중복부터 필터링한다(1시간 동안 기억). 새 명령이면 inbox에 기록하고, 워커가 행을 선점해 PG사를 호출한다. 성공하면 결과를 발행하고, 일시 오류면 간격을 늘려 다시 시도하며(최대 4회), 한도를 소진하면 격리 상태로 회신한다.

    승인 · 확정 거절 일시 오류 시 지수 백오프 재시도 재시도 한도 소진 시 자동 격리

    설계 의도

    Self-loop 재시도 구조복잡한 재시도 전용 인프라를 추가하지 않고 동일한 Kafka 토픽으로 재발행한다. 정상 흐름과 재시도 흐름이 완전히 동일한 파이프라인을 타므로 검증이 단순하고 견고하다.
    재시도 횟수 DB 영속화횟수를 메시지 헤더에만 두면 유실 시 무한 재시도 루프에 빠질 수 있다. DB(pg_inbox)에 시도 횟수를 영속화하여 어떤 장애 상황에서도 보장된 한도 내에서 안전하게 격리되도록 설계했다.
    동시성 경합 차단재시도와 중복 수신이 동시에 겹치더라도, DB의 주문당 1행 제약(UNIQUE)과 행 선점 잠금(SKIP LOCKED)을 통해 동일 결제건이 PG사를 중복 호출하는 사고를 원천 차단한다.

    동시성 경합 방어

    동시 요청이 겹쳐 돈·재고가 틀어질 수 있는 지점과, 그것을 막는 원자 연산을 표로 정리했다.

    #경합 지점발생 리스크방어 메커니즘원자 연산
    핵심 운영 상수 · 값과 근거 모두 코드에서 검증
    4PG 재시도 한도RetryPolicy.MAX_ATTEMPTS · 소진 시 격리대부분의 벤더 5xx 에러나 타임아웃은 수 초 내에 회복된다. 지수 백오프 기반의 4회 시도로 일시적 장애를 극복하며, 이를 초과할 경우 장기 장애로 간주하여 추가적인 중복 승인 위험을 방지하기 위해 즉시 격리 처리한다.
    1hPG 메시지 중복 방지 TTLRedis SET NX EX · PT1H메시지 재배달은 컨슈머 재시작이나 파티션 리밸런싱 직후 단시간 내에 집중 발생한다. 1시간의 만료 시간(TTL)은 해당 위험 구간을 충분히 커버하면서도 Redis의 메모리 사용량을 안정적으로 통제한다.
    P8D재고·product 멱등 TTL691200s = 7d + 1dKafka의 기본 메시지 보관 주기는 7일이므로, 이 기간 동안에는 언제든 메시지가 재배달될 위험이 존재한다. 중복 방지 TTL을 이보다 1일 더 긴 8일로 설정하여 이중 차감 및 데이터 정합성 훼손을 원천 차단한다.
    1s×5결과 처리 재시도FixedBackOff · 초과 시 events.confirmed.dlq단일 파티션 내에서 재시도가 길어지면 후속 결제 처리까지 지연되는 헤드 오브 라인 블로킹(HOLB) 현상이 발생한다. 1초 간격 5회 시도 후 실패 시 즉시 DLQ로 라우팅하여 전체 파이프라인의 병목을 해소한다.
    EOS결과 확정 커밋DB + offset + 발행 원자 1단위DB 상태 갱신과 비동기 재고 이벤트 발행이 분리되면 중간 장애 시 데이터 정합성이 깨질 수 있다. DB 트랜잭션, Kafka 오프셋 커밋, 메시지 발행을 단일 트랜잭션(EOS)으로 묶어 정확히 1회(Exactly-Once) 처리를 보장한다.
    10dDLQ 보관 기간864000000ms > 재주입 가능 기간 8dDLQ 메시지는 최대 8일(멱등 TTL) 내에 재주입되어 복구될 수 있도록 설계되었다. 따라서 DLQ 토픽의 보관 기간을 10일로 넉넉히 설정하여 복구 시기를 놓쳐 메시지가 영구 유실되는 사고를 방지한다.

    구현 과정을 세분화된 TDD 태스크 단위로 분할한다. 각 태스크는 '실패하는 테스트 작성 ➡️ 프로덕션 코드 구현'의 엄격한 순서를 정의한다.
    03execute
    구현
    정의된 태스크 단위로 실제 코드를 작성한다. 개별 태스크 완료 시마다 전체 테스트 스위트를 구동하여 기존 기능의 회귀(Regression) 결함을 방지한다.
    04ship
    마무리
    코드 리뷰 피드백 반영, 기술 문서(Wiki) 동기화, 산출물 아카이빙을 거쳐 최종 Pull Request를 생성하고 머지(Merge)를 준비한다.

    원칙 (Separation of Duties): 생성자가 자신의 결과물을 스스로 판정하지 않는다.
    구현 에이전트와 리뷰 에이전트의 역할을 분리하고, 각 단계의 전환 지점마다 사용자(Human)의 최종 확인을 거친다.

    관측과 알람

    단순 지표 수집을 넘어 4개 영역에 걸친 10개의 핵심 경보 규칙을 도입했다.
    25종의 회귀 테스트와 인위적 장애 주입을 통해 예외 징후 감지 능력을 검증했다.

    경보 그룹알람 명칭장애 징후 및 영향트리거 조건
    알람 검증: 1차로 Prometheus 규칙 테스트 도구(promtool)에 합성 시계열 25케이스를 주입해, 울려야 할 상황과 침묵해야 할 상황(오탐 방지)을 모두 회귀 테스트로 고정했다. 2차로 Toxiproxy로 네트워크를 실제로 끊거나 지연시키고 컨테이너를 강제 정지해, 라이브 스택에서 알람이 실제로 발화하는지 확인했다.
    운영 관점: 장애 인지가 고객 문의나 수동 로그 확인이 아니라 알람에서 시작되고, 격리된 결제는 관리자 화면에서 사유를 확인한 뒤 버튼 한 번으로 안전하게 종결된다. 장애 지속 시간과 건별 복구 비용을 줄이는 방향으로 운영 장치를 설계했다.

    분산 트레이싱 — 추적이 단절되는 3가지 구간

    모든 로그와 추적 정보는 4개의 마이크로서비스 전반에 걸쳐 단일 traceId로 바인딩된다.
    추적 문맥(Trace Context)이 단절될 수 있는 세 가지 구간과 그 복구 기법을 기술한다.

    traceId 하나, 이어붙임 세 번

    화면 낭독기용 요약: 하나의 traceId가 확정 요청, outbox 발행, Kafka 소비, PG의 inbox 기록과 워커 처리, 결과 소비까지 이어진다. 스레드가 바뀌어 추적이 끊기는 세 지점에서는 저장해 둔 traceparent 값으로 문맥을 복원한다.

    1프로세스 경계 (네트워크 통신)

    HTTP 또는 Kafka를 통해 다른 마이크로서비스로 넘어갈 때마다 인메모리 추적 문맥이 소실된다.

    • 추적 식별자인 traceparent(W3C 표준)를 HTTP 및 Kafka 헤더에 적재하여 전송한다.
    • 수신 측은 해당 식별자를 부모(Parent Span)로 인식하여 새로운 구간을 이어 붙인다.
    • HTTP는 Spring Boot의 계측(Instrumentation)이 자동 처리하며, Kafka는 발행 시점에 직접 주입한다.
    2비동기 처리 (아웃박스 패턴)

    메시지를 즉시 처리하지 않고 Inbox에 저장했다가 백그라운드 워커가 폴링할 때, 요청 당시의 식별자가 유실된다.

    • 수신 시점에 traceparent를 추출해(TraceparentExtractor) DB 레코드와 함께 영속화한다.
    • 백그라운드 워커가 해당 레코드를 선점(Poll)하는 순간, 저장된 식별자를 바탕으로 문맥을 복원한다.
    • 지수 백오프에 의해 수십 분 뒤에 재시도되더라도 동일한 traceId가 일관되게 유지된다.
    3스레드 컨텍스트 스위칭

    PG사 API 호출이 가상 스레드(Virtual Thread) 풀로 위임될 때, 기존 OTel Context와 MDC 로깅 식별자가 전파되지 않는다.

    • 메인 스레드에서 작업을 위임하기 직전, 현재의 추적 문맥과 로깅 식별자를 스냅샷으로 캡처한다.
    • 가상 스레드 내에서 문맥을 자동 복원하는 커스텀 래퍼 ContextAwareVirtualThreadExecutors를 도입했다.
    • 풀 내부의 어떤 가상 스레드에 할당되더라도 끊김 없는 traceId 추적을 보장한다.
    검증: 결제 한 건을 흘려보낸 뒤 4개 서비스 로그에서 같은 traceId가 모두 발견되는지 확인하는 스크립트로 이 연속성을 점검한다.
