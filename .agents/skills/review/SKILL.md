# /review — 독자 관점의 품질 평가

독자가 글의 질문과 답을 이해하고, 설명과 근거를 따라 판단할 수 있는지 평가한다. 기본 독자는 개발자이지만 글의 도메인이나 프로젝트는 처음 접하는 사람이다. 사용자가 정한 독자·목적·평가 범위를 우선한다.

대상은 현재 대화와 작업 중인 문서에서 확인한다. 대상이 여러 개이고 범위를 판단할 수 없을 때 확인한다. 문체·표기·사이트 구현 기준은 `/writing`과 저장소 `AGENTS.md`를 따른다.

## 읽고 판단하는 방법

먼저 본문 전체를 읽으며 독자가 얻어야 할 핵심 답을 파악한다. 설명이 끊기거나 다시 읽어야 하는 지점을 기록한 뒤, 코드·표·그림·참고 자료가 그 지점의 이해를 돕는지 확인한다.

| 평가 관점 | 판단할 질문 |
| :---: | :---: |
| 맥락과 목적 | 무엇을 다루고 왜 살펴보는지 알 수 있는가? 필요한 정상 동작이나 배경이 먼저 설명되는가? |
| 개념과 동작 | 용어·주체가 명확한가? 이름을 아는 데서 나아가 실제 동작을 설명할 수 있는가? |
| 서사와 인과관계 | 관측에서 분석으로, 분석에서 선택으로 넘어가는 이유가 연결되는가? 조건과 결과가 구분되는가? |
| 근거와 범위 | 주장·수치·선택에 근거가 있는가? 관측과 추정, 실험 조건과 해석 범위가 구별되는가? |
| 정보 배치와 표현 | 문단·불릿·번호·표·시각 자료가 이해를 돕는가? 중요한 정보가 반복이나 세부 설명에 묻히지 않는가? |
| 문체와 리듬 | 구체적인 주체와 동작이 보이는가? 추상적인 강조나 반복 요약 없이 문장이 자연스럽게 이어지는가? |
| 결론과 의미 | 처음의 질문에 답하는가? 확인한 성과·한계·적용 조건이나 교훈이 남는가? |

긴 문장과 문단은 읽는 데 필요한 작업을 기준으로 살펴본다. 주체를 되짚어야 하면 문장을 다듬고, 여러 조건을 기억하며 대조해야 하면 표나 목록을 검토한다. 실행 순서를 추적해야 하면 번호 목록을, 관계와 분기를 파악해야 하면 시각 자료를 검토한다. 배경과 이유를 따라 읽는 설명은 연결된 문단이 적합할 수 있다.

형식 변경의 효과는 수정 전후를 읽어 판단한다. 전제나 인과관계가 빠진 경우에는 설명을 보충하고, 시각 자료는 본문의 주장과 일치하는지와 작은 화면에서도 읽기 쉬운지를 함께 확인한다. 링크와 볼드는 핵심 근거와 내용을 찾는 데 쓰이는지 평가한다.

## 문제 선정과 개선

발견한 문제는 다음 세 요소로 구체화한다.

- **위치**: 섹션명이나 해당 문장
- **독자의 어려움**: 무엇을 이해하거나 판단할 수 없는지
- **개선 방향**: 어떤 설명·배치·표현을 바꾸면 해결되는지

핵심 주장에 영향을 주는 사실 오류와 논리의 비약, 이해를 막는 설명 누락을 우선한다. 문제가 없는 부분은 유지하고, 수정의 효과가 작은 취향 차이는 구분한다. 문제가 없으면 그 판단을 그대로 보고한다.

리뷰 요청에는 평가를 제공한다. 수정까지 요청받으면 선정한 문제를 실제로 고치고, 앞뒤 문단과 자료를 다시 읽어 연결과 정확성을 확인한다. 작업 범위와 개선 횟수는 사용자 요청에 맞춘다.

## 결과 보고

중요한 문제부터 위치·독자의 어려움·개선 방향을 간결하게 전달한다. 수정한 경우에는 실제 변경과 이해에 미치는 효과, 관련 검증 결과를 보고한다. 해결되지 않은 문제나 추가 확인이 필요한 사실은 명확히 남긴다.
