# 문장 다듬기 사례

`/writing`의 "문장 다듬기" 기준을 이 저장소의 실제 글에 적용한 사례다. 문장을 수정하거나 리뷰할 때 판단 기준을 맞추는 용도로 참고한다. 위치는 작성 시점 기준이며, 이후 본문이 바뀌었을 수 있다.

수정 후 문장은 정답이 아니라 방향을 보여 주는 예시다. 실제 수정에서는 앞뒤 문단과 문서의 표기 방식(Docs의 명사형 불릿 등)에 맞춘다.

## 번역체

영어 어순이나 "have / provide / by" 구문을 그대로 옮긴 문장은 한국어의 주어·동사 구조로 다시 쓴다.

**`docs/ddd/ddd-architectures.md`**

- 수정 전: 전통적인 계층형 아키텍처는 상위 계층이 하위 계층에 의존하는 구조를 가진다.
- 수정 후: 전통적인 계층형 아키텍처에서는 상위 계층이 하위 계층에 의존한다.
- 이유: "~하는 구조를 가진다"는 동작을 명사로 감쌌다가 "가진다"로 다시 서술한 형태다. 의존 관계를 바로 동사로 쓴다.

**`docs/java/jvm-jit.md`**

- 수정 전: 현대 JVM은 빠른 응답성과 최종 성능을 모두 만족시키기 위해 5단계의 계층형 컴파일 체계를 활용하며, 각 레벨은 컴파일 속도와 최적화 수준의 트레이드오프 관계를 가진다.
- 수정 후: 현대 JVM은 시작 직후의 응답성과 오래 실행된 뒤의 성능을 함께 얻기 위해 5단계 계층형 컴파일을 사용한다. 낮은 레벨은 빨리 실행할 수 있지만 최적화가 적고, 높은 레벨은 컴파일에 시간이 더 들지만 더 최적화된 코드를 만든다.
- 이유: "트레이드오프 관계를 가진다"는 무엇을 얻고 무엇을 내주는지 알려 주지 않는다. 맞바꾸는 대상을 직접 쓴다.

**`docs/test/testing-basic.md`**

- 수정 전: 테스트 자동화란 소프트웨어의 기능과 품질을 자동으로 검증함으로써, 개발 과정에서 반복적인 테스트를 효율적으로 수행하도록 해주며, 그 외에 다음과 같은 이점을 제공한다.
- 수정 후: 테스트 자동화는 사람이 반복하던 기능 검증을 코드로 실행하는 것이다. 코드를 변경할 때마다 같은 조건으로 다시 실행할 수 있어 다음과 같은 이점이 있다.
- 이유: "~함으로써 ~하도록 해주며 ~를 제공한다"로 정의와 효과를 한 문장에 이었다. 정의와 이점을 나누고, "효율적으로"를 실제 차이(같은 조건으로 반복 실행)로 바꾼다.

## 비유와 장식

비유를 풀어야 기술적 의미가 보이는 문장은 실제 동작과 결과로 바꾼다.

**`blog/async-payment-flow.md` — 결론 도입**

- 수정 전: 단순한 동기 confirm 플로우에서 안전한 비동기 Outbox 패턴으로 아키텍처를 진화시키며, 다음 세 가지 인사이트를 얻을 수 있었다.
- 수정 후: 동기 confirm 플로우를 비동기 Outbox 패턴으로 바꾸며 확인한 내용은 다음 세 가지다.
- 이유: "진화시키며", "인사이트를 얻을 수 있었다"는 정보를 더하지 않는다. "안전한"은 뒤에서 수치로 보여 줄 결론이므로 도입에서 미리 단정하지 않는다.

**`blog/async-payment-flow.md` — 결론의 트레이드오프 정리**

- 수정 전: 안전장치로서의 가치: Outbox 패턴은 외부 API 장애 시 시스템이 무너지지 않도록 지탱하는 가치를 데이터로 입증
- 수정 후: 클린 환경의 고지연 시나리오에서 동기 방식은 요청 1,945건을 수용하지 못했고, Outbox 방식은 수용하지 못한 요청이 없었다. 이 조건에서는 외부 API 지연이 스레드 고갈로 번지지 않았다.
- 이유: "무너지지 않도록 지탱하는 가치"는 비유를 풀어야 의미가 보인다. "입증"은 한 실험 환경의 결과보다 넓은 주장이므로, 바로 위 표의 수치와 측정 조건으로 바꾼다.

**`docs/java/completable-future.md`**

- 수정 전: `CompletableFuture`는 이러한 예외를 우아하게 복구하거나 로깅할 수 있는 전용 메서드를 제공한다.
- 수정 후: `CompletableFuture`는 전파된 예외를 받아 기본값으로 복구하거나 로그를 남기는 메서드를 제공한다.
- 이유: "우아하게"는 어떻게 처리하는지 알려 주지 않는다. 바로 아래 목록에 있는 실제 동작(기본값 반환, 로그)으로 바꾼다. API가 메서드를 갖춘 경우의 "제공한다"는 자연스러운 표현이므로 유지한다.

**`blog/ai-backend-development-workflow.md` — 결론**

- 수정 전: 지침을 지속적으로 보강해, 점점 더 안전하고 효율적인 워크플로우로 진화
- 수정 후: 발견한 위반 사례를 체크리스트와 에이전트 정의에 반영해, 같은 실수가 다음 작업에서 반복되지 않게 함
- 이유: "안전하고 효율적인 워크플로우로 진화"는 무엇이 바뀌는지 드러나지 않는다. 본문 "위반 사례가 규칙으로 쌓인다" 절에서 설명한 실제 동작을 쓴다.

## 추상적 효과어

"유지보수성", "유연성", "안정성"이 실제로 무엇을 바꾸는지 대상·원인·동작으로 풀어 쓴다.

**`docs/java/inheritance.md`**

- 수정 전: 상속을 사용하면 코드의 중복을 줄이고 공통 관리가 가능해져 유지보수성이 향상된다.
- 수정 후: 상속을 사용하면 공통 필드와 메서드를 부모 클래스에 한 번만 작성하고, 부모 클래스를 수정하면 모든 자식 클래스에 반영된다.
- 이유: "유지보수성이 향상된다"를 실제로 줄어드는 작업(중복 작성, 여러 곳 수정)으로 바꾼다.

**`docs/ddd/aggregate-and-root.md`**

- 수정 전: 거대한 애그리거트는 동시성 문제를 유발하고 시스템의 유연성을 떨어뜨린다.
- 수정 후: 애그리거트가 크면 한 번에 불러오는 객체가 많아지고, 여러 사용자가 같은 애그리거트를 동시에 수정하다 충돌할 가능성도 커진다.
- 이유: 아래 목록(로딩 속도·메모리, 동시 수정 충돌)에 이미 근거가 있는 효과로 풀어 쓴다. "유연성 저하"는 어떤 변경이 어려워지는지 본문에 근거가 없다. 의미를 추측해 채우지 말고 작성자에게 확인한다.

**`blog/msa-transition-decisions.md` — "실패를 전제한 설계" 절**

- 수정 전: 결제 시스템의 안정성은 단일 트랜잭션 의존을 벗어나 실패 지점을 격리하고 최종적 일관성을 맞추는 데 있다.
- 수정 후: 서비스마다 DB가 분리되어 하나의 트랜잭션으로 묶을 수 없으므로, 실패할 수 있는 지점을 서비스별로 나누고 재시도와 보상 트랜잭션으로 상태를 맞춘다.
- 이유: "안정성은 ~에 있다"는 선언을 이 글에서 실제로 선택한 방법과 그 이유로 바꾼다. 재시도와 보상은 같은 절의 목록에 있는 내용이다.

## 과장과 단정

근거가 뒷받침하는 범위까지만 주장한다.

**`docs/java/map.md`**

- 수정 전: `HashMap`은 내부적으로 배열 (해시 버킷)을 사용하여 데이터를 저장하며, 덕분에 $O (1)$의 압도적인 탐색 성능을 제공한다.
- 수정 후: `HashMap`은 키의 해시 값으로 배열(해시 버킷)의 인덱스를 바로 계산하므로 평균 $O(1)$에 값을 찾는다. 해시 충돌이 많아지면 탐색이 느려지며, 이에 대한 대응은 아래 "해시 충돌" 절에서 다룬다.
- 이유: $O(1)$은 충돌이 적을 때의 평균이다. "압도적인"을 빼고, 문서가 이미 다루는 예외 조건과 연결한다.

**`docs/ddd/intro-to-ddd.md`**

- 수정 전: 이러한 복잡성을 근본적으로 해결하기 위해 도메인 주도 설계(Domain-Driven Design, DDD) 방법론을 활용한다.
- 수정 후: 도메인 주도 설계(Domain-Driven Design, DDD)는 이러한 복잡성을 다루기 위해 도메인 모델을 설계의 중심에 두는 방법론이다.
- 이유: DDD를 적용해도 비즈니스 복잡성 자체는 남는다. "근본적으로 해결"은 방법론이 약속하는 범위를 넘는다.

**`docs/ai-assisted-development/ai-assistant-how-it-works.md`**

- 수정 전: AI 어시스턴트는 단순 자동 완성 도구가 아닌, 개발자의 생산성을 획기적으로 향상시키는 강력한 도구이다.
- 수정 후: AI 어시스턴트는 다음 코드를 채우는 데 그치지 않고, 위 목록처럼 코드 분석부터 수정·테스트 작성까지 수행한다.
- 이유: "획기적으로", "강력한"은 근거 없는 평가다. 바로 앞 목록이 보여 주는 차이(자동 완성과 달리 수행하는 작업의 범위)를 쓰거나, 목록으로 충분하다면 문장을 삭제한다.

## 줄이면 안 되는 내용

결론을 간결하게 다듬더라도 불리한 결과와 측정 조건은 남긴다.

**`blog/async-payment-flow.md` — 결론의 비교표**

"상시 저지연 결제 완료 시간: 동기 213ms (우위) / Outbox 308ms" 행과 "저지연 환경에서 Sync가 유리한 것은 자연스러운 결과"라는 설명은 Outbox 방식에 불리한 결과다. 결론을 줄이더라도 이 행을 지우거나 고지연 결과만 남기면, 독자는 Outbox 방식이 모든 조건에서 낫다고 오해한다.

## 고치지 않는 문장

수정할 이유를 설명할 수 없으면 그대로 둔다.

- `docs/network/transport-layer.md`: "TCP는 전송 계층의 대표적인 프로토콜로, 신뢰성 있는 데이터 전송을 보장한다." — "보장한다"는 단정 표현이지만, 재전송과 순서 제어로 전달을 보장하는 것은 TCP의 정의다. 근거가 있는 단정이므로 유지한다.
- `docs/java/completable-future.md` 등에서 API·클래스가 기능을 갖춘 경우의 "~를 제공한다"는 자연스러운 표현이다. "제공한다"라는 단어만 보고 번역체로 판단하지 않는다.
- `blog/ai-backend-development-workflow.md`: `## 위반 사례가 규칙으로 쌓인다` — 짧은 문장형 제목으로 절의 내용(위반 사례를 체크리스트에 반영)을 바로 전달한다. 다른 표현으로 바꿀 이유가 없다.

## 기술 오류가 의심되는 문장

문체를 다듬다가 사실 관계가 의심되면 의미를 바꾸지 않고 별도로 보고한다.

**`docs/redis/sentinel.md`**

> 레디스는 따로 백업 설정을 하지 않으면 모든 데이터가 사라지게 되고 서비스 전체 장애로 이어지게 되는데, 이를 방지하기 위해 레디스는 센티넬이라는 고가용성 솔루션을 제공한다.

문체로는 "~되고 ~되는데"로 이어지는 긴 문장이다. 그런데 이 문장은 백업 설정이 없을 때의 데이터 유실과, 센티넬의 역할인 장애 감지·자동 페일오버를 하나의 인과로 묶고 있다. 데이터 보존은 RDB·AOF 같은 영속화 설정이 맡는다. 문장만 매끄럽게 다듬으면 "센티넬이 데이터 유실을 막는다"는 잘못된 인과가 더 자연스럽게 읽힌다. 이런 경우 문장을 고치기 전에 "도입부가 백업과 고가용성을 같은 문제로 설명하고 있음"을 검토 항목으로 보고하고, 의미 수정은 작성자의 확인을 받는다.
