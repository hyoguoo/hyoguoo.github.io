# /writing — 콘텐츠 작성과 편집

이 글의 도메인이나 프로젝트를 처음 접하는 개발자가 배경과 동작을 이해하고, 글에서 제시한 판단과 결과를 자기 말로 설명할 수 있게 작성한다. 사용자가 지정한 독자·목적·수정 범위를 우선한다.

## 글의 목적과 설명 순서

작성에 앞서 독자가 글에서 얻어야 할 답을 정하고, 그 답을 이해하는 데 필요한 내용을 배치한다.

- **Blog**: 실제 경험이나 질문을 중심으로 맥락, 관측, 분석, 선택, 결과를 연결한다. 사례에서 확인한 범위에 맞춰 의미와 교훈을 설명한다.
- **Docs**: 개념이 해결하는 문제, 동작 원리, 사용 조건을 설명한다. 독자가 적용하거나 구분할 수 있도록 예시와 경계를 제시한다.

도입에는 글을 이해하는 데 필요한 상황과 질문을 둔다. 시스템의 역할이나 정상 동작을 알아야 문제를 이해할 수 있다면 이를 먼저 설명한다. 구체적인 현상과 영향을 제시해 읽을 이유를 전달한다.

용어와 배경은 필요한 지점에서 소개한다. 프로젝트 고유 명칭은 역할까지 설명하고, 같은 대상을 일관된 이름으로 부른다. 이전 글과 외부 링크는 더 깊이 확인할 자료로 제공하며, 현재 글의 핵심 설명은 본문에서 완결한다.

섹션은 독자의 질문이 바뀌는 지점에서 구분한다. 앞에서 제시한 관측이나 의문이 다음 분석·선택으로 이어지도록 연결한다. 내부 구현은 해당 현상이나 판단을 설명하는 깊이까지 다룬다.

## 문장과 표현 형식

한 문단은 하나의 논점을 전개한다. 이어지는 문장이 앞 문장의 이유·조건·예시·결과를 설명하도록 구성하고, 논점이 달라지면 문단을 나눈다. 주체와 지시 대상이 분명한 문장을 쓰며, 문장의 길이는 설명에 필요한 정보와 읽는 호흡에 맞춘다.

긴 설명에서는 독자가 무엇을 기억하고 비교해야 하는지 살펴본 뒤 표현 형식을 고른다.

| 전달할 내용 | 적합한 표현 | 선택할 때 확인할 점 |
| :---: | :---: | :---: |
| 배경, 이유, 해석, 인과관계 | 문장과 문단 | 앞뒤 설명을 자연스럽게 따라갈 수 있는가 |
| 독립적인 조건, 특징, 확인 항목 | 불릿 | 항목을 각각 읽고 파악할 수 있는가 |
| 실행 순서, 시간 순서, 단계별 판단 | 번호 목록 | 주체와 행동, 다음 단계로 넘어가는 이유가 보이는가 |
| 같은 기준으로 비교할 대상과 수치 | 표 | 공통점과 차이를 가로·세로로 비교하기 쉬운가 |
| 주체 간 관계, 구조, 분기, 상태 변화 | 시각 자료 | 관계를 한눈에 이해하는 데 도움이 되는가 |

표현을 바꿀 때는 실제 이해가 쉬워지는지를 기준으로 판단한다. 짧은 정의는 본문에서 바로 설명할 수 있고, 여러 조건을 대조해야 하는 긴 설명은 표나 목록이 유용할 수 있다. 인과관계에 필요한 설명이 빠져 있다면 먼저 그 내용을 보충한다.

목록은 간단한 항목에는 명사구를, 동작과 이유를 설명할 때는 완결된 문장을 사용한다. 번호 목록의 각 단계에는 독자가 따라가는 데 필요한 설명을 함께 둔다.

## 문체와 강조

- 본문은 `~다.`체를 사용한다. 제목·표·짧은 목록에는 명사형을 사용할 수 있다.
- 소제목은 해당 절의 대상을 구체적으로 드러내는 명사형을 기본으로 한다.
- 동작과 결과를 구체적인 주체·조건·변화로 표현한다. 중요하다는 수식이나 상투적인 비유보다 사실과 설명으로 의미를 전달한다.
- 문장의 구조와 길이는 내용에 맞춘다. 반복되는 설명은 합치고, 결론에는 본문에서 확인한 답과 그 의미를 담는다.

| 구분 | 제목 언어 | 본문 볼드 |
| :---: | :---: | :---: |
| Blog | 한글 기본, 기술 용어·고유명사는 공식 표기 | 핵심 원인·판단·성과·한계를 빠르게 찾도록 선별적 사용 |
| Docs | 영문 기본, 상세 표기는 AGENTS.md 참조 | 사용하지 않음 |

Blog의 볼드는 주변 설명과 대비될 정도로 핵심 구절에 집중한다. 성과를 강조할 때는 해석에 필요한 조건과 한계도 함께 읽히도록 배치한다.

## 사실과 참고 자료

프로젝트의 사건과 수치는 코드·로그·실험 기록으로, 기술의 동작과 제약은 해당 버전의 공식 문서·구현으로 확인한다. 관측한 사실, 그 사실로부터의 해석, 설명용 예시를 구분한다. 작성자의 경험·행동·감정·조사 순서는 제공된 기록의 범위에서 서술한다.

수치에는 측정 대상·단위·조건·비교 범위를 붙인다. 결과를 해석할 때는 실패한 조건, 성능이 악화된 지표, 실험의 한계도 반영한다. 확인이 필요한 내용은 검증한 뒤 사용하고, 확인되지 않은 부분은 불확실한 범위를 드러낸다.

참고 링크는 독자가 핵심 주장과 수치를 검증할 수 있는 원본을 우선한다. 한 자료가 여러 내용을 뒷받침하면 대표 지점에서 연결하고, 기초 개념은 필요한 설명을 본문에 쓴다. 재현 절차나 원본 필드처럼 상세 확인을 위한 내용은 본문의 흐름에 맞춰 별도 절로 정리할 수 있다.

## 코드·표·시각 자료

자료를 제시할 때는 무엇을 확인해야 하는지 안내하고, 자료가 글의 주장과 어떻게 연결되는지 설명한다. 코드와 SQL은 실제 구현과 설명용 축약을 구분한다. 그림에는 등장 주체·관계·읽는 방향을 드러내고, 수치의 단위와 실제 관측·예시의 범위를 표시한다.

표는 가운데 정렬(`:---:`)을 기본으로 하며, 긴 설명은 가독성에 따라 왼쪽 정렬을 사용할 수 있다. 마크다운 셀 너비를 맞추기 위한 공백이나 구분선 길이 조정은 하지 않는다.

사이트에서 시각 자료를 구현할 때는 다음 기준을 적용한다.

- 흐름과 관계를 자동 배치하기에 적합하면 Mermaid를, 정밀한 비교 배치나 반응형 구성이 필요하면 SVG·Astro 컴포넌트를 사용한다.
- 흐름도는 위에서 아래로 읽는 구성을 기본으로 하고, 비교 그림은 좌우 배치 등 내용에 맞는 방향을 선택한다.
- Astro 컴포넌트를 쓰는 글은 `.mdx`로 작성한다. 본문에 컴포넌트를 불러오고 HTML·SVG·CSS는 별도 컴포넌트에서 관리한다.
- 본문은 마크다운으로 작성하고 일반 설명이나 Mermaid 노드에 `<b>`, `<div>` 등의 HTML을 직접 넣지 않는다. Blog의 볼드는 마크다운 `**`를 사용한다.
- 그림의 문구는 한글을 기본으로 하고 기술 명칭은 공식 표기를 유지한다. 색상과 텍스트를 함께 사용해 의미를 전달하며 SVG에는 접근성 설명을 제공한다.
- Mermaid 노드에 배경색을 지정하면 글자색도 지정한다. 모든 시각 자료는 라이트·다크 테마와 모바일에서 글자·대비·넘침을 확인한다.

## 기존 글 편집과 완료 점검

요청한 수정 범위에서 독자의 이해에 영향을 주는 문제부터 고친다. 구조와 표현은 개선하되, 검증된 사실·수치·기술적 조건·판단 근거를 보존한다. 중복과 주변 설명은 정리하고, 필요한 상세 자료는 독자가 찾을 수 있는 위치에 둔다.

편집 후에는 처음 읽는 독자의 관점에서 앞뒤 문단과 섹션을 연결해 읽는다.

- 글의 질문, 분석 근거, 선택 이유, 결과를 본문만으로 설명할 수 있는가?
- 용어와 주체가 필요한 시점에 소개되고, 원인·조건·결과가 연결되는가?
- 문단·목록·표·시각 자료가 각각 전달할 내용을 이해하기 쉽게 만드는가?
- 코드·그림·수치의 해석이 원본과 일치하며, 결론이 확인한 범위에 맞는가?
- 참고 링크와 강조가 핵심 내용을 찾고 검증하는 데 도움이 되는가?

콘텐츠 경로·메타데이터·내부 링크는 저장소 `AGENTS.md`를 따른다. 수정한 글의 `lastUpdated`를 갱신하고, MDX·시각 자료를 변경했다면 빌드와 필요한 화면 표시를 확인한다. 상세 품질 평가에는 `/review`를 사용한다.
