# /writing — 콘텐츠 작성과 편집

이 글의 도메인이나 프로젝트를 처음 접하는 개발자가 배경과 동작을 이해하고, 글에서 제시한 판단과 결과를 자기 말로 설명할 수 있게 작성한다. 사용자가 지정한 독자·목적·수정 범위를 우선한다.

## 작성 전 기존 글과 구성 확인

새 글을 쓰거나 구조를 크게 바꿀 때는 본문 작성 전에 다음을 확인한다. 부분 수정은 대상 문서의 기존 구성과 요청 범위를 기준으로 한다.

1. 독자의 선행 지식과 이번 글에서 답할 질문을 확인한다. 이미 아는 기초 설명과 후속 단원의 세부 사항은 현재 개념을 이해하는 데 필요한 만큼만 넣는다. 사용자가 삭제한 내용은 최신 범위로 반영하며, 이전 구성안에 있다는 이유로 복원하지 않는다.
2. 같은 카테고리·문서 유형의 관련 글 1~2개를 읽는다. 새 카테고리이면 가까운 기술의 같은 유형 문서를 고른다. 소제목의 깊이, 문단 길이, 명사형 불릿, 코드 해설과 표·그림의 쓰임을 확인해 기존 톤을 맞춘다. 기술적 사실은 별도로 검증한다.
3. 독자가 설명·비교·추적해야 할 대상을 목차에 배치한다. 처리·설정 순서는 번호로, 독립 조건·항목은 불릿으로, 비교 대상은 표로 찾을 수 있게 구성한다. H2는 큰 개념, H3는 그 아래에서 따로 구분할 동작·조건·사례에 사용한다.
4. 아래 기준으로 작성한 뒤 `전달 전 검증`을 수행한다. 형식 선택과 설명의 연결이 어려우면 [style-examples.md](style-examples.md)의 'Docs의 설명 위계와 비교 자료' 사례를 읽는다. 표·그림·목록의 개수는 고정하지 않는다.

## 글의 목적과 설명 순서

작성에 앞서 독자가 글에서 얻어야 할 답을 정하고, 그 답을 이해하는 데 필요한 내용을 배치한다.

- **Blog**: 실제 경험이나 질문을 중심으로 맥락, 관측, 분석, 선택, 결과를 연결한다. 사례에서 확인한 범위에 맞춰 의미와 교훈을 설명한다.
- **Docs**: 개념이 해결하는 문제, 동작 원리, 사용 조건을 설명한다. 독자가 적용하거나 구분할 수 있도록 예시와 경계를 제시한다.

도입에는 글을 이해하는 데 필요한 상황과 질문을 둔다. 시스템의 역할이나 정상 동작을 알아야 문제를 이해할 수 있다면 이를 먼저 설명한다. 구체적인 현상과 영향을 제시해 읽을 이유를 전달한다.

용어와 배경은 필요한 지점에서 소개한다. 프로젝트 고유 명칭은 역할까지 설명하고, 같은 대상을 일관된 이름으로 부른다. 이전 글과 외부 링크는 더 깊이 확인할 자료로 제공하며, 현재 글의 핵심 설명은 본문에서 완결한다.

섹션은 독자의 질문이 바뀌는 지점에서 구분한다. 앞에서 제시한 관측이나 의문이 다음 분석·선택으로 이어지도록 연결한다. 내부 구현은 해당 현상이나 판단을 설명하는 깊이까지 다룬다.

## 문장과 표현 형식

한 문단은 하나의 논점을 전개한다. 첫 문장에서 무엇을 설명하는지 드러내고, 이어지는 문장이 앞 문장의 이유·조건·예시·결과를 설명하도록 구성하며, 논점이 달라지면 문단을 나눈다. 문장 사이는 접속사를 덧붙이기보다 설명 순서로 연결한다. 문장을 하나씩 바꿔도 흐름이 어색하면 원인·현상·대응·결과 순으로 설명 순서를 다시 짠다. 주체와 지시 대상이 분명한 문장을 쓰며, 문장의 길이는 설명에 필요한 정보와 읽는 호흡에 맞춘다.

초안부터 독자가 해야 할 작업에 맞춰 표현 형식을 고른다. 짧은 설명에서도 비교 대상이나 구성 관계가 있으면 표·그림을 검토한다.

| 전달할 내용 | 적합한 표현 | 선택할 때 확인할 점 |
| :---: | :---: | :---: |
| 배경, 이유, 해석, 인과관계 | 문장과 문단 | 앞뒤 설명을 자연스럽게 따라갈 수 있는가 |
| 독립적인 조건, 특징, 확인 항목 | 불릿 | 항목을 각각 읽고 파악할 수 있는가 |
| 실행 순서, 시간 순서, 단계별 판단 | 번호 목록 | 주체와 행동, 다음 단계로 넘어가는 이유가 보이는가 |
| 같은 기준으로 비교할 대상과 수치 | 표 | 공통점과 차이를 가로·세로로 비교하기 쉬운가 |
| 문법·API·구현 방식의 차이 | 같은 입력·목적의 코드와 결과, 필요하면 대응표 | 어떤 표현·타입·동작이 달라졌는지 바로 비교할 수 있는가 |
| 주체 간 관계, 구조, 분기, 상태 변화 | 시각 자료 | 관계를 한눈에 이해하는 데 도움이 되는가 |

표현을 바꿀 때는 실제 이해가 쉬워지는지를 기준으로 판단한다. 짧은 정의는 본문에서 바로 설명할 수 있고, 여러 조건을 대조해야 하는 긴 설명은 표나 목록이 유용할 수 있다. 인과관계에 필요한 설명이 빠져 있다면 먼저 그 내용을 보충한다.

Docs에서는 설명의 연결과 항목의 구분을 함께 살핀다. 정의와 원인·동작·결과는 문단으로 연결하고, 독립 조건·구성 요소는 불릿으로, 순서가 있는 작업은 번호로 나눈다. 긴 문단에 여러 항목이 묻히면 필요한 부분을 목록으로 분리한다. 문장을 쉽게 고친다는 이유로 한 문장마다 새 문단을 만들거나, 모든 설명을 불릿으로 바꾸지 않는다.

어려운 표현은 대상과 동작을 직접 적어 풀어 쓴다. 예를 들어 '디렉토리는 빌드가 읽을 범위를 정한다'보다 어떤 파일을 어디에 두고 어떤 설정을 추가하는지 설명한다. 문장을 각각 줄인 뒤에도 앞 문장이 다음 문장의 이유·전제가 되는지 다시 읽는다. 접속사 추가나 문장 합치기만으로 연결을 대신하지 않는다.

목록은 간단한 항목에는 명사구를, 동작과 이유를 설명할 때는 완결된 문장을 사용한다. 번호 목록의 각 단계에는 독자가 따라가는 데 필요한 설명을 함께 둔다.

## 문장 다듬기

독자가 문장을 해석하는 데 힘을 쓰지 않고 기술적 사실과 판단 근거에 집중할 수 있게 쓴다. 목표는 문장을 인상적으로 만드는 것이 아니라 정확하고 자연스럽게 읽히게 하는 것이다. 판단이 애매하면 같은 디렉토리의 `style-examples.md`에 정리한 이 저장소의 수정 사례를 참고한다.

- **번역체**: "~하는 구조를 가진다", "트레이드오프 관계를 가진다", "~함으로써 ~하도록 해주며", 추상명사를 겹친 주어처럼 영어 어순을 옮긴 문장은 한국어 화자가 쓰는 주어·동사 구조로 다시 쓴다. API가 기능을 갖춘 경우의 "제공한다"처럼 자연스러운 표현까지 기계적으로 바꾸지 않는다.
- **비유와 장식**: 비유를 풀어야 기술적 의미가 보이는 문장("아키텍처를 진화시킨다", "무너지지 않도록 지탱한다", "우아하게 처리한다")은 실제 동작과 결과로 바꾼다. 비유 자체를 금지하지는 않으며, 복잡한 개념의 이해를 실제로 돕는 비유는 유지한다.
- **추상적 효과어**: "유연성이 높아진다", "유지보수성이 향상된다", "안정성을 확보한다", "효율적으로 처리한다"는 실제로 무엇이 달라지는지 설명해야 정보가 된다. 무엇이(데이터·상태·컴포넌트·작업), 왜(원인·제약·근거), 어떻게(동작·변경·결과) 달라지는지 쓴다. 일반 원칙이 중요하면 구체적인 사례를 먼저 설명한 뒤 일반화한다.
- **과장과 단정**: "압도적", "획기적", "극대화", "근본적으로 해결", "완벽하게", "무조건", "입증"은 근거가 그 범위를 뒷받침할 때만 쓴다. 관측한 사실, 그 사실의 해석, 추측을 문장에서 구분한다. 프로토콜 정의처럼 근거가 분명한 단정은 그대로 쓴다.
- **용어**: 한국어 개발 문서에서 익숙한 표기(캐시, 큐, 타임아웃, 재시도, 데드락)는 억지로 번역하지 않는다. 기술 명칭·설정값·상태값·코드 식별자(Kafka, Outbox, p95, `READY`)는 원래 표기를 유지한다. 같은 대상은 글 전체에서 같은 표기로 부른다.

간결하게 쓰되 짧게 만드는 것 자체를 목표로 삼지 않는다.

| 줄이는 것 | 남기는 것 |
| :---: | :---: |
| 같은 결론을 반복하는 문장 | 판단에 필요한 전제 |
| 표·그림으로 이미 전달한 설명 | 기술적 제약과 예외 조건 |
| 의미를 더하지 않는 수식어와 강조 문장 | 선택한 대안의 근거와 트레이드오프 |
| 일반론을 반복하는 도입과 마무리 | 실패 가능성, 불리한 결과, 측정 조건 |

기술적으로 필요한 설명이라면 문장이 다소 길어져도 남긴다.

## 문체와 강조

- 본문은 `~다.`체를 사용한다. 제목·표·짧은 목록에는 명사형을 사용할 수 있다. 종결 어미와 문장 길이를 기계적으로 통일하지 않고, 자연스럽게 읽히는 리듬을 우선한다.
- 소제목은 제목만 읽어도 그 절에서 무엇을 다루는지 알 수 있게 쓴다. "핵심 아이디어", "핵심 가치"처럼 어느 글에나 붙을 수 있는 제목은 절의 실제 내용으로 바꾼다.
    - **Docs**: 해당 절의 대상을 드러내는 명사형을 기본으로 한다.
    - **Blog**: 명사형을 기본으로 하되, 절의 결론을 전달하는 짧은 문장형 소제목을 쓸 수 있다(예: "위반 사례가 규칙으로 쌓인다").
- 독자를 가르치려 드는 어조, 과장된 감탄, 답을 바로 이어 쓰는 수사적 질문을 피한다.
- 결론에는 본문에서 확인한 답과 그 의미를 담고, 본문의 요약을 반복하거나 새로운 주장을 덧붙이지 않는다.

| 구분 | 제목 언어 | 본문 볼드 |
| :---: | :---: | :---: |
| Blog | 한글 기본, 기술 용어·고유명사는 공식 표기 | 핵심 원인·판단·성과·한계를 빠르게 찾도록 선별적 사용 |
| Docs | 영문 기본, 상세 표기는 AGENTS.md 참조 | 사용하지 않음 |

Blog의 볼드는 주변 설명과 대비될 정도로 핵심 구절에 집중한다. 성과를 강조할 때는 해석에 필요한 조건과 한계도 함께 읽히도록 배치한다.

## 사실과 참고 자료

Docs는 일반적인 기술 개념·동작·조건을 확인 가능한 사실 중심으로 설명한다. 개인 프로젝트의 설정·전환 계획·회사 맥락·학습 일정은 사용자가 요청한 경우를 제외하고 본문에 연결하지 않는다. 커리큘럼의 프로젝트 연계 항목은 개인 실습 범위로 구분한다. 개념 설명에 필요한 작은 예제는 유지하되, 예상 결과와 직접 실행한 결과를 구분한다.

프로젝트의 사건과 수치는 코드·로그·실험 기록으로, 기술의 동작과 제약은 해당 버전의 공식 문서·구현으로 확인한다. 관측한 사실, 그 사실로부터의 해석, 설명용 예시를 구분한다. 작성자의 경험·행동·감정·조사 순서는 제공된 기록의 범위에서 서술한다.

수치에는 측정 대상·단위·조건·비교 범위를 붙인다. 결과를 해석할 때는 실패한 조건, 성능이 악화된 지표, 실험의 한계도 반영한다. 확인이 필요한 내용은 검증한 뒤 사용하고, 확인되지 않은 부분은 불확실한 범위를 드러낸다.

참고 링크는 독자가 핵심 주장과 수치를 검증할 수 있는 원본을 우선한다. 한 자료가 여러 내용을 뒷받침하면 대표 지점에서 연결하고, 기초 개념은 필요한 설명을 본문에 쓴다. 재현 절차나 원본 필드처럼 상세 확인을 위한 내용은 본문의 흐름에 맞춰 별도 절로 정리할 수 있다.

## 코드·표·시각 자료

자료를 제시할 때는 무엇을 확인해야 하는지 안내하고, 자료가 글의 주장과 어떻게 연결되는지 설명한다. 코드와 SQL은 실제 구현과 설명용 축약을 구분한다. 그림에는 등장 주체·관계·읽는 방향을 드러내고, 수치의 단위와 실제 관측·예시의 범위를 표시한다.

표는 가운데 정렬(`:---:`)을 기본으로 하며, 긴 설명은 가독성에 따라 왼쪽 정렬을 사용할 수 있다. 마크다운 셀 너비를 맞추기 위한 공백이나 구분선 길이 조정은 하지 않는다.

사이트에서 시각 자료를 구현할 때는 다음 기준을 적용한다.

- 일반 학습 Docs는 `.md`의 표·코드·Mermaid를 우선 활용한다. 기존 글의 톤과 사용자가 소스를 직접 편집하기 쉬운 구성을 유지한다.
- 흐름과 관계는 Mermaid로 표현한다. 기존 컴포넌트를 재사용하거나 Markdown·Mermaid로 전달하기 어려운 표현이 구체적으로 필요한 경우에 MDX·SVG·Astro 컴포넌트를 검토한다. 표현 자유도만을 이유로 파일 형식이나 시각 스타일을 바꾸지 않는다.
- 흐름도는 위에서 아래로 읽는 구성을 기본으로 하고, 비교 그림은 좌우 배치 등 내용에 맞는 방향을 선택한다.
- Astro 컴포넌트를 쓰는 글은 `.mdx`로 작성한다. 본문에 컴포넌트를 불러오고 HTML·SVG·CSS는 별도 컴포넌트에서 관리한다.
- 본문은 마크다운으로 작성하고 일반 설명이나 Mermaid 노드에 `<b>`, `<div>` 등의 HTML을 직접 넣지 않는다. Blog의 볼드는 마크다운 `**`를 사용한다.
- 그림의 문구는 한글을 기본으로 하고 기술 명칭은 공식 표기를 유지한다. 색상과 텍스트를 함께 사용해 의미를 전달하며 SVG에는 접근성 설명을 제공한다.
- Mermaid 노드에 배경색을 지정하면 글자색도 지정한다. 시각 자료는 글자·대비·넘침을 고려해 작성하며, 실제 화면 검증 여부와 범위는 저장소 `AGENTS.md`의 화면 검증 규칙을 따른다.

## 기존 글 편집

요청한 수정 범위에서 독자의 이해에 영향을 주는 문제부터 고친다. 구조와 표현은 개선하되, 검증된 사실·수치·기술적 조건·판단 근거를 보존한다. 중복과 주변 설명은 정리하고, 필요한 상세 자료는 독자가 찾을 수 있는 위치에 둔다.

명시적인 요청이 없으면 다음 내용은 표현만 다듬고 의미를 바꾸지 않는다.

- 기술적 사실과 주장, 그 주장이 적용되는 범위
- 실험 수치와 단위, 측정 환경과 검증 조건
- 예외 조건과 불확실성, 장단점과 트레이드오프
- 코드 식별자와 설정값, 문서의 논리 구조와 학습 목적

문체를 다듬다가 기술적 오류가 의심되면 의미를 임의로 바꾸지 않고 별도 검토 항목으로 보고한다. 잘못된 인과를 매끄럽게 다듬으면 오류가 더 그럴듯하게 읽히기 때문이다.

많이 고치는 것보다 필요한 부분을 정확하게 고치는 것을 목표로 한다. 수정할 이유를 설명할 수 없는 문장은 그대로 둔다. 다음과 같은 과도한 교정을 하지 않는다.

- 이미 자연스러운 문장을 다른 표현으로 바꾸거나, 모든 문장을 짧게 만든다.
- 전문 용어를 일상어로 바꾸거나, 구체적인 기술 설명을 추상적인 요약으로 대체한다.
- 원문에 없는 주장·해석을 더하거나, 글을 인상적으로 만들려고 새 비유를 넣는다.
- 문서 전체를 획일적인 보고서 문체로 바꿔 글쓴이의 서술 방식을 지운다.

## 전달 전 검증

본문을 작성·수정한 뒤 사용자에게 전달하기 전에 다음 절차로 한 번 검증한다.

1. 완성한 파일을 다시 읽고 아래 관점을 실제 절·문단·자료에 대조한다. 부분 수정도 변경한 부분과 앞뒤 문맥을 읽는다.
2. 각 관점에서 확인한 위치와 판단 근거를 짚는다. 미흡한 부분은 수정하고 연결된 문맥을 다시 읽는다. 지침을 읽었다는 선언이나 빌드 통과만으로 내용 검증을 마치지 않는다.
3. 전달할 때는 실제 확인한 근거를 1~2개 짧게 보고하고, 미확인 사항은 구분한다. 검증표를 콘텐츠 본문이나 별도 파일에 매번 추가할 필요는 없다.

| 검증 관점 | 본문에서 확인할 것 |
| :---: | :--- |
| 독자와 범위 | 선행 지식에 비해 불필요한 기초 설명, 반복 안내, 요청하지 않은 개인 프로젝트·계획이 남아 있는가 |
| 쉬운 표현과 연결 | 파일·설정·동작의 대상이 구체적인가. 문단 안에서 이유와 결과를 따라갈 수 있는가. 한 문장씩 끊겨 목록처럼 읽히지 않는가 |
| 표현 형식과 기존 톤 | 순서는 번호, 독립 항목은 불릿, 비교는 표로 구분했는가. 문단만 길게 이어지거나 목록만 남아 설명이 끊기지 않는가. 기존 글의 표현 밀도와 어울리는가 |
| 사실과 근거 | 기술적 주장·수치·조건을 공식 자료·코드·실행 기록과 대조했는가. 예상과 실행 결과를 구분하고, 코드·표·그림이 같은 내용을 설명하는가 |
| 보존과 문법 | 사용자 삭제·수정 범위를 지켰는가. 전제·실패 조건·불확실성을 보존했는가. 메타데이터·링크·용어·표기가 맞는가 |

콘텐츠 경로·메타데이터·내부 링크는 저장소 `AGENTS.md`를 따른다. 수정한 글의 `lastUpdated`를 갱신하고, 문법·컴포넌트·설정 등 빌드에 영향을 주는 변경은 필요한 범위에서 빌드로 확인한다. MDX나 시각 자료를 수정했다는 이유만으로 화면 검증을 수행하지 않으며, 화면 검증은 `AGENTS.md`의 조건에 해당할 때만 진행한다. 상세 품질 평가에는 `/review`를 사용한다.
